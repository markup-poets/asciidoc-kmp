= Minimal AsciiDoc Converter in Kotlin Multiplatform: Architecture and Design

== Introduction
AsciiDoc is a powerful, semantic markup language for technical documentation. It makes it possible to generate a wide variety of output formats (HTML, PDF, ePub, man pages, etc.) from an easily readable text file.

An AsciiDoc processor reads an AsciiDoc document, creates an internal document model from it, and generates the desired output format from that model.

Kotlin Multiplatform (KMP) allows the development of a single codebase for JVM, JavaScript, and native platforms. An AsciiDoc converter built with KMP can therefore be used across platforms—for example as a CLI tool, IDE plugin, or web application.

The goal is a:

* platform-independent converter
* spec-compliant AsciiDoc support (TCK-compatible)
* clearly structured pipeline (Parse → Process → Convert → Render)
* modular and extensible design
* no external dependencies


== AsciiDoc Specification and TCK
The AsciiDoc Language Specification is developed under the Eclipse Foundation. It defines the syntax, grammar, and APIs of the language.

A central element is the *Technology Compatibility Kit (TCK)*, which ensures that implementations are correct and compatible. As long as the specification is in draft status, *Asciidoctor* is considered the reference implementation.


== Architecture and Pipeline Design
Processing is performed in clearly separated phases:

. *Parse* – Analyze the AsciiDoc source text → AST/ASG
. *Process* – Resolve includes, attributes, substitutions
. *Convert* – Transform into a target format (e.g., HTML)
. *Render* – Final output or persistence

This separation increases maintainability, testability, and extensibility.


== Parse Phase
The parser produces a platform-neutral document model (AST).

Characteristics:

* line-based processing
* state machines for complex structures
* separate inline markup processing
* no external parser libraries

Examples of AST nodes:

* Document
* Section
* Paragraph
* List / ListItem
* InlineText, Strong, Emphasis


== Process Phase
After parsing, the AST is further enriched:

* Resolve includes (`include::file[]`)
* Replace attributes (`{version}`)
* Macros and substitutions
* Validation and normalization
* Automatic content (e.g., TOC)

This phase is extensible via *DocumentProcessor* interfaces.


== Convert Phase
The converter transforms the AST into a target format.

Example interface:

[source,kotlin]
----
interface Converter<Output> {
    fun convert(document: Document): Output
}
----

Typical implementations:

* HTML
* Plain text
* Debug / AST dump

Traversal is usually done via the visitor pattern or `when` dispatch.


== Render Phase
The renderer handles the final output:

* Writing to files
* Returning data to an IDE/UI
* Optional post-processing of the format (templates, styles)

Here too, everything remains interchangeable and platform-neutral.


== Modularity and Extensibility
Recommended module structure:

* `asciidoc-core`
* `asciidoc-html`
* `asciidoc-cli`
* `asciidoc-extensions`

Extension points:

* custom block and inline syntax
* tree processors
* additional converters
* custom output targets


== Example Pipeline (Kotlin)
[source,kotlin]
----
val parser = AsciidocParser()
val ast = parser.parse(input)

val processor = AsciidocProcessorPipeline()
processor.addProcessor(TodoBlockProcessor())
processor.process(ast)

val html = HtmlConverter().convert(ast)
HtmlRenderer().render(html, outputFile)
----


== Conclusion
A minimal AsciiDoc converter in Kotlin Multiplatform can be lightweight, spec-compliant, and highly extensible. With a clean pipeline architecture, complex requirements can be implemented elegantly—without external dependencies.

Kotlin Multiplatform enables maximum reuse across all relevant platforms.
