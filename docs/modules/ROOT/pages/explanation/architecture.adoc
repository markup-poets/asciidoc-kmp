= ASG-native pipeline architecture

Markup Poet is built around a single document model: the Abstract Semantic
Graph (ASG) defined by the official AsciiDoc Language Specification. Every
phase of the pipeline — parsing, document processing, rendering — reads and
writes the same ASG types. This page explains why the project is structured
that way and what the trade-offs are.

== Why one model end to end

Many converters parse into a private internal AST and translate to a public
model at the edges. That design has a recurring failure mode: the internal
tree and the public schema drift apart, and the translation layer becomes a
place where semantics quietly get lost or invented.

Markup Poet deliberately avoids that layer. The parser emits ASG nodes
directly, mirroring the official schema; the project's original internal AST
was deleted once the ASG model covered everything it did. There is nothing to
translate, so there is nothing to drift. When the TCK compares our output
against an expected fixture, it is comparing the same structures the parser
actually built — not a lossy projection of them.

== Node axes instead of node classes

The official schema classifies nodes along axes that are plain fields:
`name` (what the node is, e.g. `paragraph`, `list`), `variant` (e.g.
`ordered` vs `unordered`), and `form` (e.g. `delimited` vs `paragraph`).
Markup Poet keeps these as fields on a small sealed hierarchy of `Block` and
`Inline` types rather than minting a Kotlin class per construct.

The consequence: supporting new syntax is usually parser work — recognizing
the text and choosing the right field values — not a schema change rippling
through every consumer. Renderers and exporters that switch on the axes keep
working when a new variant appears.

== The spec and TCK as design compass

The AsciiDoc specification is still evolving, and prose specifications are
sometimes ambiguous. The project treats the synced TCK fixtures
(`tck-quality-testing/official-tck/repository/tests/`) as ground truth when
the prose leaves room for interpretation: if a fixture shows the expected ASG
for a construct, that is what the parser produces. This keeps design debates
short and keeps compatibility measurable — the conformance gate is a script
run, not a judgment call.

== Where each concern lives

* `asciidoc-parser` — recognizing syntax and building the ASG. Zero external
  dependencies; pure text-to-graph transformation.
* `document-processing` — everything that needs context beyond a single
  parse: resolving includes, evaluating conditionals, substituting
  attributes, building the table of contents, resolving cross-references.
* `html-renderer` — turning the processed ASG into HTML, with theming kept
  strictly on the presentation side (see
  xref:explanation/theming.adoc[Theming architecture]).
* `asciidoc-asg` and `asg-graphviz-export` — alternative outputs: the
  official ASG JSON serialization and Graphviz DOT for visualization.
* `plugin-api` / `plugin-engine` / `plugin-integration` — sandboxed WASM
  extensions that transform the document before rendering or participate in
  rendering itself (see xref:explanation/wasm-plugins.adoc[Why WASM plugins]).

A handful of processing-only extension nodes (includes, conditionals, custom
block macros) exist outside the official schema; they are produced by the
parser core and consumed by document-processing, and the TCK serialization
path refuses them all — no TCK fixture contains such constructs.

== Part of a family

This converter is one member of the Markup Poet family. Its sibling, the
{url-dsl-poet}[DSL poet], approaches the same format from the other
direction: it is a Kotlin DSL that *writes* AsciiDoc, while this project
parses it. Sharing the AsciiDoc language between a writer and a
specification-oriented reader keeps both honest — documents generated by the
DSL poet are exactly the kind of input this parser aims to handle.
